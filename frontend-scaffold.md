# Next.js + Tailwind frontend

## Steps

1. Ask the user where to create the project: in the current root folder, or in
   a new subfolder (ask for its name, suggesting `frontend`). Ask this together
   with the goal question below, then wait for the answer. Do not create any
   file, folder or run any command until the user has answered.
   All later paths and commands are relative to the chosen folder (`cd` into
   the subfolder after creating it).
2. Ask the user for the project goal in 1 sentence. It is only for context;
   it does not authorize building anything. If the user doesn't give one,
   use "TBD" instead of inferring it.
3. Scaffold FIRST in the chosen folder. For the root folder use `.` (it must be
   empty); for a subfolder, replace `.` with its name (create-next-app creates
   it), then `cd` into it:
   `npx create-next-app@latest . --ts --tailwind --eslint --app --src-dir --import-alias "@/*"`. No features yet.
4. Keep the AGENTS.md generated by Next.js as is. Don't edit or remove its content. Append this section at the end:
   ```md
   ## Project rules

   - Small diffs; one feature or fix at a time.
   - Validate all client input with zod (trust boundary).
   - No new deps, DB, auth or external services without asking.
   - Don't modify unrelated code or delete existing tests.
   - Every bug fix gets a regression test.
   - Config via env vars only (see .env.example); new vars must be added to .env.example and src/lib/env.ts.
   ```
5. Create `.env.example` (with API_URL), copy it to `.env`, and make sure `.env` is in `.gitignore`.
   create-next-app ignores `.env*`, which also hides `.env.example`, so add `!.env.example` to `.gitignore`.
6. Add the example API call (see "Example API call"): the home page calls the backend `GET /health` and shows the result.
7. Add Vitest + Testing Library, a render test for `HealthStatus`, and run `npm test` to confirm setup.
8. Stop. Report what was created and the test result, then ask the user which
   feature to build first. Do not add features, endpoints, pages or
   components the user did not explicitly name.

## Done when

- create-next-app scaffold + AGENTS.md "Project rules" section.
- .env.example / .env, src/lib/env.ts, src/lib/api.ts.
- Home page shows only the HealthStatus example.
- `npm test` (the HealthStatus test), `npm run typecheck` and `npm run lint` pass.
  Nothing beyond this. Stop here.

## Structure

```
AGENTS.md                  # generated by Next.js + "Project rules" section
.env.example               # committed template (copy to .env)
.env                       # local, git-ignored
src/
  app/
    layout.tsx
    page.tsx               # example: calls backend /health
    api/<route>/route.ts   # API route handlers (if backend is needed)
  components/              # UI components (server by default)
    health-status.tsx      # example component
  lib/                     # fetchers, utils, validation (zod)
    env.ts                 # reads and validates env vars
    api.ts                 # typed fetch helper for the backend
  types/                   # shared types
tests/                     # or *.test.tsx next to components
```

## Standards

- Follow Next.js defaults from create-next-app and the docs referenced in AGENTS.md.
- TypeScript strict; App Router only (no pages/).
- Server Components by default; add "use client" only when needed (state, effects, events).
- Styling with Tailwind utility classes only; no extra UI or CSS libraries unless asked.
- Data fetching in server components or src/lib; client components don't call external APIs directly.
- API routes: validate input with zod, return proper status codes (200, 201, 400, 404, 500), never leak errors.
- Handle loading (loading.tsx), error (error.tsx) and empty states.
- Accessible markup: labels, buttons, semantic HTML.
- Dev deps for tests: vitest, @vitejs/plugin-react, jsdom, @testing-library/react, @testing-library/dom, @testing-library/jest-dom, vite-tsconfig-paths.
- Vitest 5 requires `@types/node` 22+, but create-next-app pins `^20`: install `@types/node@^24` (or the version matching your Node) together with the test deps.
- Scripts: `dev`, `build`, `lint`, `test` (vitest run), `typecheck` (tsc --noEmit).
- Test behavior (what the user sees) and API route handlers; not implementation details.
- No DB, auth or external services unless asked.

## Environment

- `.env.example` must list every env var with defaults that work with the backend skill:
  ```
  # Backend API (node-express-backend runs on PORT=3000)
  API_URL=http://localhost:3000
  ```
- Frontend runs on port 3001 to avoid conflict with the backend: `dev` = `next dev -p 3001` (PORT can't be set via .env in Next.js).
- `src/lib/env.ts` validates env with zod and exports a typed `env`; no other file reads `process.env` directly.
- Backend calls go through `src/lib/api.ts` and run on the server (server components, server actions or route handlers), so no CORS is needed.
- Only add `NEXT_PUBLIC_*` vars if a value must reach the browser; never put secrets in them.
- `.env` is git-ignored; never commit secrets.

Example `src/lib/env.ts`:

```ts
import { z } from "zod";

const schema = z.object({
  API_URL: z.string().url().default("http://localhost:3000"),
});

export const env = schema.parse(process.env);
```

Example `src/lib/api.ts`:

```ts
import { env } from "./env";

export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${env.API_URL}${path}`, {
    ...init,
    headers: { "Content-Type": "application/json", ...init?.headers },
    cache: "no-store",
  });
  if (!res.ok) throw new Error(`API ${res.status}: ${path}`);
  return res.json() as Promise<T>;
}
```

## Example API call

The home page calls the backend (`GET /health` → `{ "status": "ok" }`) on the server and shows the result. If the backend is down, it shows "unreachable" instead of crashing.

`src/components/health-status.tsx`:

```tsx
type Props = { status: string | null };

export function HealthStatus({ status }: Props) {
  return (
    <p className="text-sm">
      Backend status:{" "}
      <span className={status ? "text-green-600" : "text-red-600"}>
        {status ?? "unreachable"}
      </span>
    </p>
  );
}
```

`src/app/page.tsx`:

```tsx
import { api } from "@/lib/api";
import { HealthStatus } from "@/components/health-status";

type Health = { status: string };

export default async function Home() {
  let status: string | null = null;
  try {
    status = (await api<Health>("/health")).status;
  } catch {
    status = null;
  }

  return (
    <main className="p-8 space-y-4">
      <h1 className="text-2xl font-bold">App</h1>
      <HealthStatus status={status} />
    </main>
  );
}
```

`tests/health-status.test.tsx`:

```tsx
import { render, screen } from "@testing-library/react";
import { describe, it, expect } from "vitest";
import { HealthStatus } from "@/components/health-status";

describe("HealthStatus", () => {
  it("shows backend status", () => {
    render(<HealthStatus status="ok" />);
    expect(screen.getByText("ok")).toBeInTheDocument();
  });

  it("shows unreachable when backend is down", () => {
    render(<HealthStatus status={null} />);
    expect(screen.getByText("unreachable")).toBeInTheDocument();
  });
});
```
